## 二、总体优化框架

第二阶段优化共划分为五个大类。各类定位、核心目标与优先级关系如下表所示。

| 类别 | 定位 | 核心目标 | 优先级 |
| --- | --- | --- | --- |
| 1. 业务逻辑优化 | 保证数据正确、口径一致、业务规则闭环 | 消除字段不一致与错误关联，统一业务口径 | P0（最高） |
| 2. 性能优化 | 降低响应耗时与资源占用，提升体验 | 缓存化、图表生命周期管理、稳定抽样 | P1（高） |
| 3. 权限与安全优化 | 保护敏感数据，防止注入与越权 | 脱敏、防 XSS、鉴权与审计 | P1（高） |
| 4. 运维、交付、可维护性优化 | 提高部署、交接与长期维护效率 | 单后端、模块化、测试与文档、配置外置 | P2（中） |
| 5. 功能增强 | 扩展系统业务能力 | 增删改查、导出、登录、交互体验 | P3（按需） |

> 说明：优先级 P0 > P1 > P2 > P3。P0 与 P1 建议在第二阶段优先落地。

## 三、各类别详细说明

### 3.1 业务逻辑优化

#### 3.1.1 本类作用

业务逻辑优化是整个系统正确性的底座。人事数据由「教职工主表 + 19 张子表」按工号（`工号`）聚合而成，任何字段映射、取值口径或关联方式的偏差，都会导致页面展示为空、字段错乱，甚至前端直接报错。该类优化的目标是：**前端展示的字段结构、后端两个实现输出的字段结构、以及 Excel 原始列含义三者完全对齐**，并确保关联、排序、统计口径一致。

#### 3.1.2 当前存在问题

| 序号 | 问题 | 现状描述 | 影响 | 严重级别 |
| --- | --- | --- | --- | --- |
| B-01 | 双后端字段不一致 | Node 版 `server.js` 与 Django 版 `personnel/views.py` 输出的 JSON 字段结构不同 | 使用 Django 启动时，前端读取深层字段会得到 `undefined`，部分页面直接崩溃 | 严重 |
| B-02 | 类别字段命名混乱 | 前端部分代码引用 `professionalTitle.major`、`positionInfo.title`，而 Django 输出 `professionalTitle.series`、`positionInfo.name` | 字段名不统一，后续维护极易写错 | 严重 |
| B-03 | 用「姓名」反查工号 | `generateTableHTML` 中通过 `personnelData[i].name === cell` 反查 id | 同名教职工会出现详情点开错误对象 | 严重 |
| B-04 | 退休口径不一致 | Node 按「离退休状态」字段判断；Django 按「退休日期」是否为空判断 | 两套实现计算出的在职/退休人数不同 | 中 |
| B-05 | 子表取数规则未显式化 | `single_map` 对同一工号多条记录仅取第一条，未明确「最新/最早」规则 | 编制、岗位、职称等多条记录可能取到非最新值 | 中 |
| B-06 | 默认年份硬编码 | Node 与 Django 无晋升记录时的默认区间不一致（2020–2025 与 2020–2026） | 无晋升数据人员的图表基线不一致 | 低 |
| B-07 | 空值与缺失字段容错不足 | 前端多处直接访问 `p.positionInfo.title`、`p.staffingType.type` | 缺失字段人员进入页面时出现 `undefined` 报错 | 中 |

#### 3.1.3 问题定位与代码实例

**① 双后端字段不一致（B-01 / B-02）**

Node 版 `server.js` 输出的关键字段结构如下：

```js
// server.js（Node 后端，start.bat 默认使用）
var pos = positionMap[id] || {};
var positionInfo = {
  title: pos['岗位名称'] || '',
  level: pos['岗位等级'] || '',
  hireDate: parseDate(pos['聘用日期'])
};

var s = staffingMap[id] || {};
var staffingType = {
  type: s['编制类型'] || '',
  entryDate: parseDate(s['入编日期'])
};
```

Django 版 `personnel/views.py` 同名字段的结构却是另一套：

```python
# personnel/views.py（Django 后端）
'positionInfo': {
    'name': pos_map.get(id_, {}).get('岗位名称', ''),
    'level': pos_map.get(id_, {}).get('岗位等级', ''),
    'dept': pos_map.get(id_, {}).get('所在部门', ''),
},
'staffingType': st_map.get(id_, {}).get('编制类型', ''),  # 这里变成了纯字符串！
```

前端 `js/main.js` 按 Node 字段读取：

```js
// 部队名：专业职称这里取 major，但 Django 输出的是 series
'<div class="detail-item"><span class="label">职称</span><span class="value">' +
  (p.professionalTitle.title || '-') + ' · ' + (p.professionalTitle.major || '') +
'</span></div>'

// 编制类型这里取 staffingType.type + entryDate，但 Django 输出的是纯字符串
'<div class="detail-item"><span class="label">编制类型</span><span class="value">' +
  p.staffingType.type + ' (' + p.staffingType.entryDate + ')' +
'</span></div>'
```

**后果**：当使用 `start_django.bat` 启动时，`p.staffingType.type`、`p.positionInfo.title`、`p.skillLevel.trade` 等均为 `undefined`，页面直接报 `Cannot read properties of undefined`。

**优化目标**：确立一套「唯一字段契约」。建议以 Node 版为基准（`start.bat` 是默认入口），将 Django 版 `views.py` 的输出对齐为：

```python
# personnel/views.py（优化后：与 Node 字段完全一致）
'staffingType': {
    'type': st_map.get(id_, {}).get('编制类型', ''),
    'entryDate': parse_date(st_map.get(id_, {}).get('入编日期')),
},
'positionInfo': {
    'title': pos_map.get(id_, {}).get('岗位名称', ''),
    'level': pos_map.get(id_, {}).get('岗位等级', ''),
    'hireDate': parse_date(pos_map.get(id_, {}).get('聘用日期')),
},
```

同时建立字段映射对照表，详见 3.4.3 的文档建设部分。

**② 用「姓名」反查工号（B-03）**

当前 `generateTableHTML` 中的关联逻辑：

```js
// js/main.js（现状：用姓名反查 id，同名会错挂）
pagedRows.forEach(function(row) {
  html += '<tr>';
  row.forEach(function(cell, idx) {
    if (idx === 1) {
      var pid = null;
      for (var i = 0; i < personnelData.length; i++) {
        if (personnelData[i].name === cell) { pid = personnelData[i].id; break; }
      }
      html += '<td><span class="clickable-name" data-id="'+(pid||'')+'">'+cell+'</span></td>';
    } else {
      html += '<td>'+cell+'</td>';
    }
  });
  // 详情按钮同样用 name 反查，存在同样的同名问题
  var did = null;
  for (var j = 0; j < personnelData.length; j++) {
    if (personnelData[j].name === row[1]) { did = personnelData[j].id; break; }
  }
  html += '<td><button class="btn btn-outline" onclick="window.showDetailById(\''+(did||'')+'\')">详情</button></td>';
  html += '</tr>';
});
```

**问题**：`cell` 是纯展示文本，一旦存在同名人员，反查到的 `id` 可能与当前行不是同一个人，导致「详情」打开错误档案。

**优化目标**：让行数据在构造时就携带 `id`，渲染时直接使用，不再反查：

```js
// js/main.js（优化后：行数据自带 id，避免姓名反查）
// 约定：第一行数据中约定携带隐藏的 personId（例如 row[0] 为工号时直接作为 id）
function renderSimpleTable(type, columns, rowMapper) {
  var rows = personnelData.map(function(p) { return rowMapper(p); }).filter(function(r) { return r; });
  // 在生成行时附带 id 元数据
  rows = rows.map(function(r, i) {
    r.__pid = personnelData[i % personnelData.length].id; // 示意：实际应严谨一对一传递
    return r;
  });
  return generateTableHTML(columns, rows);
}
```

更稳妥的做法是让 `rowMapper` 返回 `{ id, cells }` 结构，`generateTableHTML` 只负责渲染，彻底消除「用展示值反查主键」的隐患。

**③ 空值与缺失字段容错不足（B-07）**

现状的深层属性直接访问：

```js
// js/main.js（现状：staffingType 可能是 undefined，直接 .type 会抛错）
'<div class="stat-value">' + p.staffingType.type + '</div>'
```

**优化目标**：统一提供安全访问工具：

```js
// js/utils.js（新增工具函数）
function safeGet(obj, path, fallback) {
  var keys = path.split('.');
  var cur = obj;
  for (var i = 0; i < keys.length; i++) {
    if (cur == null) return fallback;
    cur = cur[keys[i]];
  }
  return cur == null ? fallback : cur;
}

// 使用示例
var staffingName = safeGet(p, 'staffingType.type', '未填写');
```

#### 3.1.4 优化目标与措施汇总

| 措施 | 具体内容 | 预期收益 |
| --- | --- | --- |
| 1. 建立统一字段契约 | 以 Node 版为基准，编写字段映射对照表，令 Django 输出与 Node 完全一致 | 两套后端返回一致，前端不再报错 |
| 2. 单后端化（建议） | 若两套后端无并存必要，保留一套、删除另一套 | 从源头消除不一致，减少约一半后端维护成本 |
| 3. 以 ID 关联替代姓名关联 | 行数据构造时直接携带 `id`，渲染不再反查 | 彻底杜绝同名错挂 |
| 4. 统一退休判定规则 | 明确以「离退休状态」字段为主、退休日期为辅的判定公式 | 在职/退休统计口径统一 |
| 5. 明确子表取值规则 | 对单条类子表增加「按日期取最新」规则 | 岗位、职称、编制信息更准确 |
| 6. 统一默认年份基线 | 统一无晋升数据时的默认年份区间 | 图表基线一致 |
| 7. 空值安全访问 | 提供 `safeGet` 工具，替换深层直接取属性 | 缺失字段不再导致页面报错 |

#### 3.1.5 验收标准

- [ ] 两个后端（若均保留）对同一名测试人员输出的 JSON 各字段完全一致；
- [ ] 所有页面在缺失子表数据时均能正常渲染并显示「暂无数据」；
- [ ] 同名教职工点击详情可正确打开对应人员档案；
- [ ] 在职/退休人数在 Node 与 Django 下结果一致。

### 3.2 性能优化

#### 3.2.1 本类作用

性能优化关注系统的**响应速度、流畅度与资源占用**。当前系统每次打开页面都从 Excel 全量解析 20 张工作表，且前端 ECharts 图表在多页面切换时不断新建实例并叠加 resize 监听器，数据量增大或长时间使用后容易出现卡顿与内存上涨。该类优化目标是：**减少重复计算、控制图表生命周期、保证统计结果稳定可复现**。

#### 3.2.2 当前存在问题

| 序号 | 问题 | 现状描述 | 影响 | 严重级别 |
| --- | --- | --- | --- | --- |
| P-01 | 后端每次请求全量解析 Excel | `/api/personnel` 每次调用都解析 20 张表并重新聚合 | 数据量越大，接口响应越慢，CPU 与内存占用高 | 高 |
| P-02 | 无 HTTP 缓存 | Node 与 Django 均未设置 `Cache-Control`/ETag | 重复请求重复计算 | 中 |
| P-03 | ECharts 实例未销毁 | 每次进入仪表盘/画像都 `echarts.init`，离开页面不 `dispose` | 反复切页导致实例堆积、内存泄漏 | 高 |
| P-04 | resize 监听器重复叠加 | 每个图表初始化函数都 `window.addEventListener('resize', ...)` | 切页次数越多，回调越多 | 高 |
| P-05 | 图表随机抽样不稳定 | 散点图 `shuffle().slice(0,80)`、热力图随机取 25 人 | 统计展示不可复现 | 中 |
| P-06 | 全量数据一次性载入渲染 | 前端获取全部数据，列表页与画像共用同一份全量数据 | 首屏变慢，计算负担大 | 中 |
| P-07 | 重复线性查找 | 多处用 `for` 循环遍历 `personnelData` 按 id/name 定位 | 每次交互 O(n) 查找 | 低 |

#### 3.2.3 问题定位与代码实例

**① 后端无缓存（P-01）**

Node 版现状：每次请求都重新 `readFile` 解析 Excel：

```js
// server.js（现状：每次请求都重新解析）
if (req.url === '/api/personnel') {
  var data = buildPersonnelData();   // 每次都 XLSX.readFile + 20 张表聚合
  res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
  res.end(JSON.stringify(data));
  return;
}
```

**优化目标**：服务启动时解析一次并缓存，文件 `mtime` 变化时热更新：

```js
// server.js（优化后：内存缓存 + 文件变更热更新）
var fs = require('fs');
var CACHE = { data: null, mtimeMs: 0 };

function getPersonnelData() {
  var stat = fs.statSync(EXCEL_PATH);
  if (!CACHE.data || stat.mtimeMs !== CACHE.mtimeMs) {
    CACHE.data = buildPersonnelData();
    CACHE.mtimeMs = stat.mtimeMs;
  }
  return CACHE.data;
}

// 接口调用处改为
var data = getPersonnelData();
```

Python（Django）侧同理，将 `build_personnel_data()` 的结果缓存于模块级变量：

```python
# personnel/views.py（优化后：模块级缓存）
_CACHE = {'data': None, 'mtime': None}

def get_personnel_data_cached():
    mtime = EXCEL_PATH.stat().st_mtime
    if _CACHE['data'] is None or _CACHE['mtime'] != mtime:
        _CACHE['data'] = build_personnel_data()
        _CACHE['mtime'] = mtime
    return _CACHE['data']
```

**② ECharts 实例与 resize 监听泄漏（P-03 / P-04）**

现状：每个 `initXxxChart` 都在内部创建独立实例并新增一个 resize 监听：

```js
// js/main.js（现状：每个图表独立 init 并各自绑定 resize）
function initPieTitle() {
  var el = document.getElementById('chart-pie-title'); if (!el) return;
  var chart = echarts.init(el);   // 每次进入页面新建实例
  // ...
  window.addEventListener('resize', function() { chart.resize(); }); // 反复叠加
}
```

切页 N 次后，旧实例未被销毁，`resize` 监听器也累积了 N 份。**优化目标**：建立全局图表注册表 + 单一 resize 监听：

```js
// js/chartManager.js（新增图表生命周期管理）
var chartRegistry = [];

function registerChart(chart) {
  chartRegistry.push(chart);
  chart.__registered = true;
}

function disposeAllCharts() {
  chartRegistry.forEach(function(chart) {
    if (!chart.isDisposed()) chart.dispose();
  });
  chartRegistry = [];
}

// 全局只绑定一次 resize
window.addEventListener('resize', function() {
  chartRegistry.forEach(function(chart) {
    if (!chart.isDisposed()) chart.resize();
  });
});

// 页面切换前统一销毁
function renderPage(pageKey, parentKey) {
  disposeAllCharts();   // 切页先清理旧图表
  // ...渲染新页面
}
```

图表初始化函数相应改为：

```js
function initPieTitle() {
  var el = document.getElementById('chart-pie-title'); if (!el) return;
  var chart = echarts.init(el);
  registerChart(chart);          // 替换原来的 addEventListener('resize')
  // ...
}
```

**③ 随机抽样不稳定（P-05）**

现状：散点图与热力图使用 `shuffle` 随机抽样：

```js
// js/main.js（现状：结果每次进入页面都不同）
function shuffle(arr) { /* Fisher-Yates */ }
var data = shuffle(allData).slice(0, 80);   // 散点图随机取 80 人
```

**优化目标**：改为确定性抽样，例如按综合绩效排序取前 N：

```js
// js/main.js（优化后：确定性抽样）
function topBy(research, allData, topN) {
  return allData.slice()
    .sort(function(a, b) { return (b.researchScore || 0) - (a.researchScore || 0); })
    .slice(0, topN);
}

// 或者使用固定随机种子保证可复现
function seededShuffle(arr, seed) {
  var rand = seedPrng(seed);   // 确定性伪随机数发生器
  // 用 rand 进行 Fisher-Yates
}
```

**④ 重复线性查找（P-07）**

现状：搜索、详情、图表点击等多处以 O(n) 查找：

```js
// js/main.js（现状：多处线性查找）
for (var i = 0; i < personnelData.length; i++) {
  if (personnelData[i].id === id) { portraitSelectedPerson = personnelData[i]; break; }
}
```

**优化目标**：数据加载完成后构建一次 `id → person` 索引：

```js
// js/data.js（优化后：构建索引）
var personnelById = {};

function loadPersonnelData(callback) {
  // ...成功拿到 data 后
  personnelData = data;
  personnelById = {};
  data.forEach(function(p) { personnelById[p.id] = p; });
  // ...
}

// 后续查找 O(1)
function findPersonById(id) {
  return personnelById[id] || null;
}
```

#### 3.2.4 优化目标与措施汇总

| 措施 | 具体内容 | 预期收益 |
| --- | --- | --- |
| 1. 服务端内存缓存 | 启动时解析一次并缓存，文件 `mtime` 变化热更新 | 接口响应从「每次解析」降为「读内存」 |
| 2. 增加 HTTP 缓存与 ETag | 返回 `Cache-Control` + ETag，304 响应 | 减少网络负载与重复计算 |
| 3. 图表实例集中管理 | 维护 `chartRegistry`，切页前统一 `dispose()` | 消除实例堆积 |
| 4. 单一 resize 监听 | 仅绑定一个 `window.resize`，遍历注册表统一 `resize()` | 消除监听器泄漏 |
| 5. 确定性抽样 | 用排序取前 N 或固定随机种子替代 `shuffle` | 图表结果稳定、可复现 |
| 6. 前后端分离数据粒度 | 列表请求精简字段，画像按 id 请求详情 | 降低首屏数据量与计算压力 |
| 7. 建立 id→person 索引 | 数据加载后构建 `Map<id, person>` | 查找 O(1) |

#### 3.2.5 验收标准

- [ ] 二次请求同数据时接口命中缓存，响应时间明显下降；
- [ ] 连续切换页面 20 次后，内存与 ECharts 实例数量保持稳定；
- [ ] 同一抽样图表多次进入页面结果一致。

### 3.3 权限与安全优化

#### 3.3.1 本类作用

权限与安全优化用于保护系统中的人事敏感数据（身份证号、手机号、邮箱、考核与晋升信息），防止数据泄露、注入攻击与越权访问。该类优化目标是：**最小权限原则下展示必要信息、对用户输入与数据输出做安全转义、对配置与凭据做安全隔离**。

#### 3.3.2 当前存在问题

| 序号 | 问题 | 现状描述 | 影响 | 严重级别 |
| --- | --- | --- | --- | --- |

**① 敏感数据明文 + XSS 风险（S-01 / S-02）**

现状：直接拼接且不转义、不脱敏：

```js
// js/main.js（现状：明文 + 未转义）
```

**优化目标**：统一脱敏 + HTML 转义。先定义工具函数：

```js
// js/utils.js（新增：脱敏与转义工具）
function escapeHtml(str) {
  var div = document.createElement('div');
  div.textContent = str == null ? '' : String(str);
  return div.innerHTML;
}

function maskIdCard(idCard) {
  if (!idCard || idCard.length < 8) return idCard;
  return idCard.slice(0, 4) + '**********' + idCard.slice(-4);
}

function maskPhone(phone) {
  if (!phone || phone.length < 7) return phone;
  return phone.slice(0, 3) + '****' + phone.slice(-4);
}

function maskEmail(email) {
  if (!email || email.indexOf('@') === -1) return email;
  var parts = email.split('@');
  var user = parts[0];
  var shown = user.slice(0, 2) + '***';
  return shown + '@' + parts[1];
}
```

渲染处统一改为：

```js
// js/main.js（优化后：先转义、再脱敏）
html += '<div class="detail-item"><span class="label">身份证号</span>' +
        '<span class="value">' + escapeHtml(maskIdCard(p.idCard)) + '</span></div>';
```

> 说明：数据展示一律先 `escapeHtml`，再按需 `maskXxx`；内部管理角色可通过「点击查看明文」并记录日志的交互获取完整值。

```js
// js/search.js（优化后：防抖处理）
function debounce(fn, delay) {
  var timer = null;
  return function() {
    var args = arguments;
    var ctx = this;
    clearTimeout(timer);
    timer = setTimeout(function() { fn.apply(ctx, args); }, delay);
  };
}

var doSearch = debounce(function(keyword) {
  var results = fuzzySearchPersonnel(keyword);
  renderSearchSuggestions(results);
}, 250);

input.addEventListener('input', function() {
  var keyword = this.value.trim();
  if (!keyword) {
    suggestions.style.display = 'none';
    return;
  }
  doSearch(keyword);
});
```

## 五、风险与注意事项

| 风险 | 说明 | 应对措施 |
| --- | --- | --- |
| 双后端迁移风险 | 统一/删除后端可能影响现有启动方式 | 迁移前先整理字段契约并准备测试样例 |
| 敏感数据改造风险 | 脱敏与权限可能影响日常使用 | 提供「管理员可见明文 + 操作留痕」折中方案 |
| Excel 回写风险 | 新增 CRUD 涉及数据回写 | 回写前备份原文件，采用「先备份后更新」 |
| 前端重构回归风险 | 模块化拆分 1570 行文件易引入回归 | 拆分前后分别功能冒烟测试 |
| 性能优化验证不足 | 缓存与图表治理需真实数据验证 | 建立性能基线，优化后对比响应时间与内存 |
